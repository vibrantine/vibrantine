Independent repository audit

Strong engineering, with trust-boundary gaps.

Vibrantine has unusually good automated coverage, disciplined architecture, and documentation for a pre-1.0 library. The implementation largely matches its parent-mediated composition, governed provider access, persistence, and minimal-surface principles. It is not yet ready to claim that the contract is fully enforced at every boundary: four high-severity defects allow malformed receipts, invalid money, unbounded tool output, or observational callbacks to undermine guarantees that the design calls structural.

● Conditional — close P1 findings before the next trust-boundary release
Scope: source, tests, docs, CI, package artifact Baseline: clean worktree Runtime: Windows · Python 3.12.12 Version: 0.6.0 + 27 commits

Executive summary

Green gates are meaningful here, not decorative. The remaining risk is concentrated in adversarial and invalid states that the current suite does not generate.

4 P1 findings affecting contract integrity, accounting, boundedness, or errors-as-values.
5 P2 findings affecting resilience, privacy, authoring safety, and file-operation semantics.
540 Tests passed. Eight platform/live integration or evaluation cases skipped.
95–100% Measured branch coverage across the six central runtime modules.
What this means: the project does not need a broad rewrite. The architecture is coherent. The best next move is a narrow hardening arc: enforce the receipt, enforce numeric honesty, centralize safe observation, and make growing tool results genuinely bounded and resumable.

P1

Result envelope population invariants are documented, but not enforced

Confirmed defect

The ruling record says success and partial carry output, while failure and partial carry error, and says “the runtime already provides” that guarantee. CommissionResult declares all population fields optional without a model validator. Dispatch stamps and returns an author-produced result without checking the status/output/error relationship.

A success with neither output nor error, a failure with output and no error, and a partial with no error all validate today. The MCP server’s specialized revalidation also accepts them because it uses the same model.

Evidence: contract.py:137–151; dispatch.py:183–238; ruling: One result envelope, one class. Targeted construction reproduced all three malformed envelopes.
Recommendation: add an after-model validator that enforces the three population states and forbids contradictory fields. Add dispatch tests for third-party custom _run returns and MCP round trips. This tightens behavior to the existing ruling; it does not add vocabulary or public surface.
P1

CostMetrics accepts negative, NaN, and infinite values

Confirmed defect

Model catalog prices and run budgets are carefully restricted to finite, non-negative numbers. The receipt itself is not. A custom Commission can return negative dollars/tokens, NaN, or infinity in CostMetrics.

NaN is especially dangerous: ordinary less-than/greater-than comparisons are false, so the cost-honesty warning and budget comparisons can be bypassed after a poisoned child cost enters a parent’s rollup. This violates the structural accounting premise even if every real provider call was metered correctly.

Evidence: contract.py:87–106. Targeted construction accepted estimated_usd=-1, float("nan"), float("inf"), and negative token counts. By contrast, run configuration and model catalog construction reject invalid money.
Recommendation: constrain dollars to finite ge=0 and token counts to ge=0. Couple this with F-01 so a third-party result is rejected at construction/dispatch before it can enter a rollup. Add NaN-focused tests because it behaves differently from ordinary out-of-range numbers.
P1

GrepTool’s max_matches does not bound one file’s work or one match’s size

Confirmed defect

GrepTool advertises a bounded result. Internally, _grep_file reads the whole file, splits every line, and builds every matching GrepMatch before the outer loop applies max_matches. A file with a million matching lines creates a million objects even when the caller requests one.

A matching line is also returned in full with no character cap. One minified or generated line can therefore make the returned payload arbitrarily large while truncated remains false.

Evidence: grep.py:151–181 applies the cap after grep.py:222–234 materializes all matches and full lines. The LLM-facing description at lines 81–99 says the output is bounded.
Recommendation: stream matching lines from each file and stop at the global cap. Add a per-line character bound with explicit truncation metadata and a resumption mechanism (file + line + character offset, or a cursor). Test a huge matching line and a file with far more matches than the cap.
P1

on_progress is called unsafely and can let exceptions cross the boundary

Confirmed defect

ProgressEvent is explicitly “observability, not a control surface.” The Gatekeeper protects on_llm_call and on_dispatch: it passes copies, catches callback exceptions, and logs them. on_progress is invoked directly.

A callback that raises during Commission._emit is converted into an internal Commission failure. More seriously, the overflow flag and persistence-failure emission sites run outside the _run exception backstop, so the callback exception can escape run_commission entirely. Observability can therefore change both the result and the errors-as-values guarantee.

Evidence: contract.py:779–782; dispatch.py:353–360; dispatch.py:704–712. Compare the guarded callbacks in _gatekeeper.py:297–342.
Recommendation: centralize progress delivery behind one private safe-emitter that catches/logs callback failures. Use it from _emit and dispatch. Test raising callbacks at loop start, overflow, and persistence-failure sites.
P2

ReadTool truncates long lines without a way to retrieve the remainder

Principle violation

Read is documented as the canonical resumable tool. Pagination is line-based, but each returned line is independently cut at 30,000 characters. For a one-line file, truncated can be false even though most of the line was discarded, and changing the line offset cannot reach the missing characters.

Evidence: read.py:116–123 computes truncation only from remaining lines; read.py:135–141 drops the remainder of a long line. This conflicts with the project instruction that large results are cursors over data and truncation must be recoverable.
Recommendation: add character-level continuation for long lines or represent returned lines as resumable segments. At minimum expose separate line-truncation metadata; a visible marker alone signals loss but does not make it recoverable.
P2

Commission authoring accepts invalid configurations that fail late

Systemic risk

The class-definition checks are an excellent fail-fast mechanism, but they cover only identity presence, generic/ClassVar agreement, and the extension hook. Several invalid states remain easy for inexperienced authors:

  • duplicate toolbox names make one child unreachable and may send duplicate provider tool definitions;
  • a child named conclude collides with the framework exit tool and can never be dispatched;
  • empty/invalid provider tool names and empty descriptions are accepted;
  • negative caps/iterations and fractions above 1 are accepted;
  • non-Pydantic identity types can be expressed at runtime and fail only when schema generation is attempted.
Evidence: contract.py:415–520; llm_tools.py:71–100 and 186–190. Targeted construction accepted negative policy values and target_input_fraction=2.0.
Recommendation: extend existing definition/construction validation rather than adding a new surface. Validate Pydantic contract types and non-empty identity at class definition; validate numeric policies and toolbox uniqueness/reserved names in __init__. Add exact, beginner-readable error messages.
P2

Several “bounded” tools cap the returned value only after unbounded acquisition

Robustness gap

Context size is bounded more consistently than process memory. Read loads and splits the full file; Shell’s communicate() buffers all stdout/stderr before clipping; Fetch materializes the full decoded body; Glob and ListDir sort complete result sets before slicing. A large input can exhaust memory or block the event loop even when the requested result cap is tiny.

Evidence: read.py:112–119; shell.py:216–234; fetch.py:146,194; glob.py:121; list_dir.py:123.
Recommendation: treat payload bounds and execution-resource bounds as two separate properties. Stream/spool Shell and Fetch, stream Read while counting lines, and document where exact totals require a full scan. Add memory-oriented regression cases without inventing a public concurrency knob.
P2

Full-record persistence can retain authentication material without warning

Privacy risk

Persistence intentionally stores complete inputs and LLM traces. Fetch explicitly invites Authorization headers. If a Fetch call is made by an LLM and recording is enabled, the header may appear both in the child’s serialized input and in the parent’s raw tool-call trace. Shipped filesystem/SQLite backends do not provide redaction, and current operator docs do not warn that records may contain secrets.

Generic automatic redaction is not simple—the application owns what is sensitive—but the absence of a warning/convention is a dangerous default for an observability feature.

Evidence: fetch.py:26–29,73; dispatch.py:612–645 serializes full input/result and retains the raw LLM trace.
Recommendation: document the data-retention threat model now. Establish an authoring convention using secret-aware field types or explicit exclusion for credentials, and test it through both input records and LLM traces. Review local file permissions. Do not add a speculative redaction registry without a named consumer and ruling.
P2

No-overwrite safety flags use check-then-write operations

Concurrency defect

WriteTool(create_only=True) checks path.exists() and later calls write_bytes(). A concurrent creator between those operations is overwritten, contradicting the promised refusal. MoveTool(overwrite=False) has the same check-then-move race, with platform-dependent rename behavior.

Evidence: write.py:97–110; move.py:110–139.
Recommendation: implement create-only writes with an atomic exclusive create (xb / equivalent). Define and test a cross-platform atomic or explicitly best-effort no-overwrite strategy for moves. Include a race test where practical.
P3

TextPart, ImagePart, and AudioPart discriminator fields lack descriptions

Confirmed drift

Runtime introspection found exactly three fields without descriptions: the type Literal on each public content-part model. All other fields across 81 imported Pydantic model classes were described, and no model exceeded the 20-field limit.

Evidence: contract.py:295–334. This conflicts with the explicit “every Field has a populated description” discipline.
Recommendation: declare each discriminator with Field(default=..., description=...) and add a package-schema introspection test so direct subclasses receive the same protection the factory gives consumer models.
P3

CI does not build the artifact or lock coverage; the manual checklist has drifted

Governance gap

CI runs the right core matrix—lint, format, strict types, and tests on two operating systems and two Python versions—but does not use a locked sync, build the wheel, inspect package contents, smoke-install it, or enforce coverage. Those checks exist only in a manual release checklist last passed before the current MCP work.

The checklist still records 393 passed / 7 skipped and a 36-name surface; this review observed 540 / 8 and 35 frozen exports. Its date makes the old facts honest historical evidence, but not current release evidence.

Evidence: ci.yml:40–52; pre-release checklist, Validation Gates.
Recommendation: use uv sync --locked --extra mcp in CI and add one package job that builds and isolated-smoke-installs the wheel. Consider a source-only branch coverage floor after excluding live examples. Refresh the checklist only at a real release pass.
P3

Model is frozen, but its params mapping is mutable after validation

Consistency risk

Model is a frozen dataclass and is described as the one stable definition of a model profile. Its params value is the caller’s original mutable dictionary. It can change between calls—or after catalog validation—and can even gain a framework-owned key that the initial catalog check had refused.

Evidence: models.py:45–76; llm_tools.py:284–295 spreads the live mapping into each provider call.
Recommendation: take an immutable defensive snapshot at construction or catalog build (including nested values as far as supported), then test that later caller mutation cannot alter a running profile.

5. Confirmed strengths and promises that hold

A useful review says what can be trusted now, not only what is wrong.

Boundary and architecture

  • One sanctioned interior hook remains _run.
  • run_commission and dispatch enforce entry/inside-run roles.
  • Nested runs and hand-built contexts are refused.
  • Run IDs and parent IDs are threaded through one dispatch seam.
  • MCP adapters do not grow CallContext or the top-level API.

Errors and control

  • Ordinary exceptions from custom _run methods become failure values.
  • Task cancellation deliberately propagates as CancelledError.
  • Call, time, and spend fuses share a run-wide breaker.
  • New dispatches and provider calls are refused after a halt.
  • Run-level and node-level budget vocabulary is kept distinct.

Cost, provenance, and records

  • Provider pricing has one formula and current default facts.
  • Paid calls without usage fail when accounting is armed.
  • Provider and dispatch logs are copied before live callbacks see them.
  • Persistence failures do not normally destroy work results.
  • Filesystem run IDs are path-contained; SQLite uses bound parameters.

Public and schema surfaces

  • Closed vocabularies and public signatures are exact-lock tested.
  • Generic parameters are checked against identity ClassVars.
  • The factory rejects missing/blank nested field descriptions.
  • Strict type checking is clean with no ignored production diagnostics.
  • Tool descriptions generally follow the LLM-facing selection pattern.

Tools and adapters

  • Tools consistently require explicit absolute filesystem paths.
  • Growing results usually expose totals and visible truncation.
  • Fetch classifies retryability by HTTP outcome.
  • MCP requests/results and adapter diagnostics are byte-bounded.
  • MCP transport/decoder exceptions do not expose internal exception text.

Delivery quality

  • The source-layout package imports only through installation.
  • The wheel excludes tests and includes required prompt assets.
  • An isolated install imports the full public surface.
  • CI covers Windows/Linux and the Python floor/latest tested line.
  • Current docs are internally link-clean and the worktree began clean.

6. Recommended remediation order

Sequence changes by dependency: make the receipt trustworthy first, then harden the operations that produce it, then automate regression proof.

Close the receipt boundary

Fix F-01 and F-02 together. Enforce status/output/error and finite non-negative cost/token invariants. Add direct, dispatch, persistence, parent-render, and MCP tests.

Make observation non-interfering

Fix F-04 with one private callback-delivery helper and fault-injection tests for every progress emission site.

Restore bounded, resumable tool semantics

Fix F-03 and F-05, then address the acquisition risks in F-07. Start with Grep because its advertised bound is currently false.

Harden authoring and destructive semantics

Fix F-06 and F-09 without expanding the public surface: validate earlier and use atomic filesystem primitives.

Set the privacy contract

Resolve F-08 through an explicit ruling or documentation convention before adding machinery. Test whatever policy is chosen against both records and traces.

Lock in the gains

Close F-10–F-12, add package/build gates, refresh release evidence, and rerun live integrations/evals with an explicit spend authorization.

7. Limitations and confidence

This is a comprehensive repository review, not a claim that every runtime environment or model behavior was exercised.

Not exercised

  • Paid OpenRouter integration calls and three live-model efficacy evals.
  • The live DeepWiki MCP integration.
  • Remote GitHub Actions execution; only its configuration was inspected.
  • The external Base Coder consumer repository.
  • A current OSV/pip-audit vulnerability advisory scan.
  • High-volume performance, memory, and provider-rate benchmarks.

Confidence

  • High for F-01, F-02, F-03, F-04, F-05, F-09, and F-10: direct construction or code path proves the issue.
  • High for package, lint, type, test, lock, link, and default-model confirmations.
  • Medium-high for F-06–F-08, F-11, and F-12: behavior is clear, while the best policy/fix needs project judgment.
  • Not assessed for live answer quality; passing contract tests do not substitute for evals.
Release decision: continuing development on the current pre-1.0 branch is reasonable. A tagged release that emphasizes a trustworthy contract should wait for F-01 through F-04. The remaining P2/P3 work can be sequenced, provided limitations are documented and the false boundedness claim in Grep is not shipped unchanged.
